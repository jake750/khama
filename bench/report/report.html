Summary

The idea. Khama is a working application used by video editors. Several of its technical decisions were constants chosen without measurement: one global FFmpeg threshold to find scene changes, a guessed “+1” to translate the user’s quality setting to the GPU encoder, and separation settings copied from another implementation. The project takes each of these decisions, builds the theory and a reproducible benchmark around it, and replaces the constant with an algorithm or a value that is justified by the measurements. Each result ships in the app, so the work is both a study and an engineering contribution.

What was done

  • Axis C: own shot-boundary detector (Rust, in the app). Soft-binned HSV histograms on a 3×3 grid, a structural luma signal, adaptive thresholds with a robust median/MAD estimator, flash rejection, and an adaptive twin-comparison for dissolves, fades and wipes. Evaluated on a 204-transition synthetic test set with exact labels and on a hand-labelled film trailer, with a dev/test split, a parameter search and an ablation study.
  • Axis A: compression study of x264, x265, SVT-AV1 and Intel Quick Sync H.264/HEVC: 636 encodes of 12 open test sequences, each scored with VMAF, PSNR and SSIM, compared by BD-rate. The study gives a calibration table that maps the user’s CRF to the hardware quality value reaching the same VMAF.
  • Axis B: separation evaluation of the app’s own STFT and ONNX pipeline on the MUSDB18 test set with BSS Eval v4: 11 configurations of chunk margin, overlap, gain compensation and mask type, compared with paired Wilcoxon tests.
  • Tooling: a khama-bench binary that runs the app’s real Rust code, plus Python scripts that rebuild every table and figure in this document from scratch.

1The application and the problem

Khama prepares media for video editing. It downloads from video sites (through yt-dlp), converts files to editing formats (ProRes, DNxHR, H.264/H.265 proxies), detects scene changes, silences and black frames, and separates voice from music with a neural network that runs locally. It is written in Rust (back end, FFmpeg orchestration, signal processing, ONNX inference) and React (interface), packaged with Tauri 2 for Windows and Android, and has an Arabic and English interface.

The method is the same on each axis:

  1. state the theory;
  2. build a dataset with ground truth;
  3. tune on one half of the data and report on the other;
  4. compare with the previous behaviour;
  5. ship the result in the app and say plainly what the data does not support.

2Axis C: shot-boundary detection

A shot is a continuous take. A shot boundary is either a hard cut between two consecutive frames or a gradual transition over several frames (cross-dissolve, fade through black, wipe). The detector compares consecutive frames with features that stay stable within a shot and change across shots.

2.1 Frame features

Soft-binned HSV histogram. Pixels are converted to HSV. Dark and grey pixels, whose hue is unstable, go into separate grey bins indexed by value, which gives 8×3×3 colour bins plus 6 grey bins (78 in total). To stop a slight colour drift from jumping a pixel into the next bin, each pixel is spread over its two nearest bins on every axis by trilinear interpolation (hue is circular):

$$h_b = \frac{1}{N}\sum_p w_b(p),\qquad \sum_b w_b(p) = 1.$$

Distance. For normalised histograms, $D(p,q) = \tfrac12\sum_b |p_b-q_b| = 1-\sum_b\min(p_b,q_b)\in[0,1]$. A global histogram ignores where colours are, so the detector also compares 3×3 block histograms:

$$d(t) = \alpha\,D(H_t,H_{t-1}) + (1-\alpha)\,\frac19\sum_{b=1}^{9} D(H_t^b,H_{t-1}^b).$$

Structural signal. Two shots of the same scene can share a palette. A 32×18 luma thumbnail $Y_t$ gives a second signal, $e(t) = \frac{1}{|\Omega|}\sum_x |Y_t(x)-Y_{t-1}(x)|/255$, which reacts to a change of layout even when the colours stay the same.

2.2 Adaptive threshold for cuts

The typical level of $d(t)$ depends on the content (an action scene against a static interview), so the threshold follows the local statistics. They are computed on a window around $t$ that excludes $t-1..t+1$, so that a cut does not raise its own threshold:

$$d(t)\ \ge\ \max\big(\tau_{min},\ c(t)+k\,s(t)\big),\qquad c=\operatorname{med}(d),\quad s = 1.4826\,\operatorname{med}|d-\operatorname{med}(d)|.$$

The median and scaled MAD are robust: unlike the mean and standard deviation, other cuts in the window do not inflate them. The structural signal $e$ has its own threshold of the same form, and a cut is reported when either signal fires at a local maximum.

Flash rejection. After a camera flash, the frames look like the frames before it. With $\delta(i,j)=\max(D(f_i,f_j), e(i,j))$, a candidate at $t$ is rejected when, for some $j\in\{1,2,3\}$, $\delta(t-1,t+j) < 0.35\,\delta(t-1,t)$ (start of a flash) or $\delta(t-1-j,t) < 0.35\,\delta(t-1,t)$ (end of a flash).

2.3 Gradual transitions: adaptive twin comparison

During a dissolve each frame-to-frame change is small, but the changes add up. This builds on Zhang et al. (1993):

  1. A run starts when $d(t)$ exceeds a low threshold $T_{low}=\max(\ell_{min}, c_p+k_{low}s_p)$. This threshold is computed on the frames before $t$ only and held fixed during the run, because the transition frames must not raise their own threshold.
  2. The run continues while $d$ stays above $T_{low}$ (one quiet frame is tolerated).
  3. The run is accepted if it lasts at least $L_{min}$ frames and the accumulated change $D(f_s,f_e)$ exceeds $G_{min}$. This rejects slow camera motion.

A fade-out and a fade-in separated only by flat frames (luma standard deviation below 6/255) are merged into one transition.

2.4 Evaluation protocol

  • Synthetic dataset with exact labels, the approach used to train and test TransNet and DeepSBD.
    • Open Xiph.org footage is cut into random shots of 1.2–3.4 s.
    • The shots are joined by cuts (55 %), dissolves (16 %), fades (14 %) and wipes (15 %).
    • Hard cases are included: 10 % of cuts join two parts of the same clip, and 25 % of shots contain a 1–2-frame flash that must not be reported.
  • Matching is one-to-one within ±2 frames, giving precision $P$, recall $R$ and $F_1 = 2PR/(P+R)$.
  • Dev/test split. Parameters are tuned on the first half of the videos and every number below is from the second half.
    • Stage 1 searches 344 cut configurations.
    • Stage 2 searches 27 gradual configurations.
  • Baselines: FFmpeg’s scene score with the threshold swept from 0.05 to 0.6, plus a real film trailer (Sintel, CC-BY) labelled by hand.

2.6 In the application

The detector replaces FFmpeg’s rule in two places: “Still frames → at scene change” in the Download tab, and the Convert tab’s tool “Detect scene changes”.

The result is a list of time-code chips:

  • a hard cut is shown as one time;
  • a gradual transition is shown as a start–end range.

From the chips the user can split the file at these points or copy the times into an editor.

3Axis A: codec study and calibration of hardware encoders

3.1 Quality metrics

  • PSNR is $10\log_{10}(255^2/\mathrm{MSE})$. For 4:2:0 video the planes are weighted 4:1:1: $\mathrm{PSNR}_{YUV}=(4\,\mathrm{PSNR}_Y+\mathrm{PSNR}_U+\mathrm{PSNR}_V)/6$.
  • SSIM (Wang et al., 2004) compares local luminance, contrast and structure.
  • VMAF (Netflix, model v0.6.1) is a support-vector regression trained on subjective scores. It fuses visual information fidelity at 4 scales, a detail-loss metric and a motion feature into a 0–100 score; 93–95 is commonly taken as visually transparent.

3.2 BD-rate

Each encoder sweeps its quality parameter, giving a rate-distortion curve. To compare two encoders with one number, the Bjøntegaard delta rate averages the horizontal gap between their curves over the common quality range:

$$\Delta R = \exp\!\Big(\frac{1}{Q_{hi}-Q_{lo}}\int_{Q_{lo}}^{Q_{hi}}\big[\ln R_{test}(Q)-\ln R_{ref}(Q)\big]\,dQ\Big)-1.$$

$\ln R(Q)$ is interpolated with monotone PCHIP, the current practice, instead of the original cubic polynomial, which can oscillate. BD-rate is computed per clip; the median is reported.

3.3 Calibrating the hardware quality scale

The calibration has three steps:

  1. For each CRF $c$ used by an app preset and each clip $k$, the target is $V^*_k(c)=\mathrm{VMAF}_{x264}(c)$.
  2. The clip’s monotone hardware curve is inverted to find the value $q_k(c)$ that reaches $V^*_k$.
  3. The table value is the median over clips, $q(c) = \operatorname{med}_k q_k(c)$.

H.264 hardware is matched to libx264 and HEVC hardware to libx265. The table replaces crf + 1.

3.4 Material and results

Material. 12 open Xiph.org sequences of 4 s each, stored losslessly at 720p. They cover fast motion, pans, fine detail and text, water, talking heads and screen content.

Encodes. 636 in total: 11 x264, 8 x265, 9 SVT-AV1, 12 h264_qsv and 13 hevc_qsv quality values per clip.

Machine. Intel i5-1135G7 with Iris Xe, so only Quick Sync can be measured. NVENC fails on a driver API mismatch (and the MX350 has no NVENC unit), and Tiger Lake cannot encode AV1.

The old rule gave the GPU encoder more quality than the user asked for, especially at the “small file” setting (+3.9 VMAF at CRF 30), so its files were larger than needed. The calibrated values hit the requested quality in the median and cut hardware files by 14 % (H.264) and 17 % (HEVC).

The mean absolute per-clip error is unchanged (1.3 and 2.2 VMAF), because it comes from the content: no single mapping can follow every clip. Removing it would need a per-file quality search, which is too slow for the app. Only Intel Quick Sync could be calibrated on the available hardware; NVENC and VideoToolbox keep the old rule until they can be measured.

4Axis B: evaluation of voice/music separation

4.1 Pipeline

Khama implements the STFT and its inverse in Rust to match the model’s PyTorch front end: periodic Hann window, $N=7680$, hop $H=1024$, reflect padding, and the first 3072 bins (up to ≈17.6 kHz). The inverse uses weighted overlap-add,

$$\hat x(n) = \frac{\sum_m w(n-mH)\,\mathrm{IDFT}\{Y(m,\cdot)\}(n-mH)}{\sum_m w^2(n-mH)},$$

which reconstructs the input exactly when $Y = X$; a unit test checks this to within $10^{-3}$.

The model, UVR-MDX-NET-Voc_FT running in ONNX, maps a 5.92 s chunk to the vocal spectrogram. Long signals are processed in chunks:

  • Each chunk keeps its centre and discards a margin at both edges, where the model lacks context.
  • Neighbouring chunks may share an overlap, cross-faded with complementary raised-cosine weights.

The accompaniment is either the mix minus the voice (subtraction) or a Wiener-like soft mask, $M=|\hat V|^2/(|\hat V|^2+|X-\hat V|^2)$.

4.2 Metrics and protocol

Metrics. BSS Eval v4 (museval) splits each estimate into $s_{target}+e_{interf}+e_{artif}$ and reports SDR, SIR and SAR. Following SiSEC 2018, each track is summarised by the median over 1 s windows and the dataset by the median over tracks. A join SNR is also measured within ±0.1 s of each chunk boundary, where the margin and overlap settings act.

Data and runs. The 50 MUSDB18 test tracks (7 s previews, 44.1 kHz stereo). Every configuration runs through the app’s own Rust code.

Conclusions.

  • Chunking settings do not matter at this scale. The overlap’s effect is statistically detectable but about a thousandth of a decibel. A 1 s margin would need about 50 % more model runs for no significant gain.
  • The soft mask is clearly worse on every track. The model already outputs the vocal spectrogram directly; re-deriving it through a ratio mask brings mixture energy back (lower SIR) and smears transients (lower SAR).
  • The 1.021 gain trades accompaniment SIR against SAR and sits between the two extremes.

The app therefore keeps its settings, now as a measured result instead of an assumption. The peak memory is about 2.55 GB, dominated by the model, and the real-time factor was 1.37 on an otherwise idle machine.

5Implementation and reproducibility

  • In the app (Rust):
    • scenes.rs: the detector, with unit tests on synthetic frames (a cut is found; motion, a flash and a fade are handled correctly).
    • convert.rs: the calibration tables and their interpolation.
    • separate.rs: parameterised chunking.
  • khama-bench is a separate binary, built with a Cargo feature, that runs exactly the app’s code on dataset files and writes JSON. The benchmark therefore measures what users run, not a re-implementation.
  • Python scripts (bench/scenes, bench/codecs, bench/separation) build the datasets, run the grids, can resume interrupted runs, and write every CSV and figure in this document. bench/REPORT.md holds the theory, protocols and tables.
  • Scale of the work: 22 commits, 73 files changed and about 8 200 lines added on the pfe branch, which is merged with the released version 0.3.3 and builds for Windows and Android.

6Limitations, future work and proposed plan

Limitations

  • Shot detection.
    • The synthetic set uses one encoder setting and 25 fps.
    • Only one real film is labelled.
    • Wipes and very slow dissolves remain the hardest cases.
  • Codecs.
    • One machine, and only Intel Quick Sync among the hardware encoders.
    • 720p clips of 4 s each.
    • The calibration fixes the median, not the per-clip error.
  • Separation. 7-second previews contain only one or two chunk joins, so the join SNR is noisy.

Possible extensions

  • Label more real material, for example the ClipShots or RAI public benchmarks, and compare with a learned detector such as TransNet V2, for accuracy and for cost on a phone.
  • Calibrate NVENC and Apple VideoToolbox on suitable machines.
  • Add a fast per-file quality search for “exact VMAF” exports.
  • Run full-length MUSDB18 tracks to study the joins with more statistical power.
